## Secuencia de llamadas tras autenticarse

1. **Validación inmediata en `Login.tsx`.**  
   - Apenas el usuario vuelve de Cognito, `fetchAuthSession()` comprueba si ya hay tokens vigentes.  
   - Si los hay, dispara `checkUserStatus()` que:
     1. Llama a `ProfileServices.getProfile()` (`GET /profile` sobre `VITE_API_URL_PROFILE`) y cachea la respuesta en `localStorage`.
     2. Evalúa que el perfil tenga `birth_date`; si falta, redirige al onboarding de datos.
     3. Usa `LocationServices.checkLocationStatus(profile.id)` para garantizar que exista una ubicación guardada; este helper reutiliza `ProfileServices.getProfileLocation()` (`GET /location?id_profile=…&table_name=userprofile`), cachea el resultado y define `DataContext.setLocation`.  
     4. Si la ubicación no existe, envía al paso de onboarding de ubicación; si todo está completo, vuelve a la ruta original que disparó el login.

```
4. **Chequeo y cacheo de ubicación.**  
   - `LocationServices.checkLocationStatus()` primero revisa `localStorage` y, si no encuentra datos, llama a `ProfileServices.getProfileLocation`.  
   - Define `hasLocation`, guarda la última ubicación obtenida y expone helpers para limpiar/consultar el estado.  
   - Es invocado desde `Login`, `ProfileContext` y `ProtectedRoute`, por lo que siempre ocurre después de `getProfile()`.

```
```16:135:src/services/LocationServices.ts
  checkLocationStatus: async (
    profileId?: string | number
  ): Promise<LocationStatus> => {
    if (!profileId) {
      return { hasLocation: false };
    }

    try {
      const storedLocation = JSON.parse(
        localStorage.getItem("location") || "{}"
      );

      if (storedLocation?.id !== null) {
        return {
          hasLocation: storedLocation?.id !== null,
          locationData: Array.isArray(storedLocation)
            ? storedLocation[0]
            : storedLocation,
        };
      }

      const response = await ProfileServices.getProfileLocation(
        profileId.toString(),
        "userprofile"
      );

      let locationExists = false;
      if (response?.data) {
        if (Array.isArray(response.data)) {
          const lastLocation = response.data[response.data.length - 1];
          locationExists =
            response.data.length > 0 &&
            lastLocation?.latitude &&
            lastLocation?.longitude;
          localStorage.setItem("location", JSON.stringify(lastLocation));
        } else if (response.data.latitude && response.data.longitude) {
          locationExists = response.data.latitude && response.data.longitude;
          localStorage.setItem("location", JSON.stringify(response.data));
        } else {
          localStorage.setItem("location", "{}");
        }
      }

      localStorage.setItem(
        "userHasLocation",
        locationExists ? "true" : "false"
      );

      return {
        hasLocation: !!locationExists,
        locationData: response?.data,
      };
    } catch (error) {
      console.error("Error checking location status:", error);
      return { hasLocation: false };
    }
  },
```

```
5. **Guardas de ruta y orden de validaciones.**  
   - Cada ruta privada pasa por `ProtectedRoute`, que encadena:
     1. `fetchAuthSession()` (si no hay tokens, redirige a `/auth/login`).  
     2. Carga del perfil (desde contexto o `localStorage`; si falta, vuelve a llamar `ProfileServices.getProfile()`).  
     3. Validación de onboarding (`birth_date`, `localitys`, flags).  
     4. Validación de ubicación (`LocationServices.checkLocationStatus`).  
   - Cualquier falla en los pasos anteriores deriva al flujo correspondiente (login, onboarding personal, onboarding de ubicación).
```

```
10. **Inyección del token en cada request posterior.**  
    - `axiosInstance` añade `Authorization: Bearer <token>` en todos los requests (exceptuando ciertas rutas públicas) reutilizando `fetchAuthSession()`. Si Cognito devuelve 401/refresh vencido, redirige a `/auth/login`. Gracias a esto, una vez autenticado, cualquier servicio (`ProfileServices`, `LocationServices`, etc.) ya viaja con el token correcto y puede seguir llamando endpoints adicionales (por ejemplo, para ver el equipo, los torneos, feeds de comunidad, etc.) en el mismo orden en el que los componentes los necesitan.
```

### Orden resumido de llamadas tras autenticarse

1. `fetchAuthSession()` → verifica tokens (Login, ProtectedRoute, ProfileContext).  
2. `ProfileServices.getProfile()` (`GET /profile`).  
3. (Solo nuevos) `ProfileServices.register()` (`POST /register`).  
4. `LocationServices.checkLocationStatus()` → puede invocar `ProfileServices.getProfileLocation()` (`GET /location`).  
5. Onboarding condicional según `profile.birth_date`, `profile.localitys`, `profile.team`.  
6. Acceso a rutas privadas (layouts) y arranque de WebSocket de notificaciones.  
7. Cada petición subsecuente (tanto a `VITE_API_URL_PROFILE` como al resto de microservicios) usa `axiosInstance` con el bearer token, por lo que los módulos de torneos, comunidad, entrenamiento, etc., van cargando su información cuando las vistas correspondientes se montan.

Con esta guía podés seguir todo el pipeline de autenticación y conocer exactamente qué servicios se invocan y en qué orden lógico se ejecutan después de que Cognito entrega un usuario autenticado.
